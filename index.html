Threat modeling, briefly

  • Assets. What are we protecting, and for whom?
  • Adversaries. Who would attack it, and what do they want?
  • Surfaces. Where does untrusted input cross a trust boundary?
  • Mitigations. What controls reduce likelihood or impact?
A threat model is a story you can tell on a whiteboard. If it doesn't fit on a whiteboard, it's an architecture diagram.

Fixing a SQL injection

Parameterize the query — do not interpolate user input.

--- a/api/users.py
+++ b/api/users.py
@@ -12,9 +12,12 @@ def lookup_user(request):
     username = request.GET.get("u", "")

-    # Vulnerable: user input is concatenated into the SQL string.
-    query = "SELECT id, email FROM users WHERE name = '" + username + "'"
-    rows = db.execute(query).fetchall()
+    # Parameterized query: the driver binds `username` as a value,
+    # not as part of the SQL grammar.
+    rows = db.execute(
+        "SELECT id, email FROM users WHERE name = ?",
+        (username,),
+    ).fetchall()

     return JsonResponse({"users": [dict(r) for r in rows]})

Defense in depth

No single control is load-bearing. Stack them.

Network — segment, firewall, mTLS between services
Application — input validation, authn/authz, output encoding
Data — encryption at rest, least-privilege access, audit
Process — code review, threat modeling, incident response
